# Технічне завдання (ТЗ)
## Розробка мультитранспортного асинхронного шлюзу-балансувальника JSON-RPC 2.0 на Rust

---

## 1. Загальний опис системи
Необхідно розробити високонавантажений, асинхронний шлюз-балансувальник навантаження (**Message-Level Gateway & Load Balancer**) корпоративного рівня на мові програмування **Rust**.

Додаток виступає єдиним центральним вузлом (точкою входу) для підключення різнородних клієнтів і розподілу їхніх запитів на пул ізольованих бекенд-серверів. Система повинна забезпечувати роботу 29 унікальних транспортних протоколів (15 базових та 14 WebSocket-style адаптерів), уніфікувати вхідні дані на рівні повідомлень, транслювати їх «насліпо» (без десеріалізації бізнес-payload) та надавати можливість асинхронного зворотного зв'язку від серверів до клієнтів (Server-Initiated Push) з урахуванням специфіки кожного транспорту.

---

## 2. Конфігурація та Динамічне Середовище
Додаток не повинен містити жорстко закодованих (hardcoded) мережевих параметрів. Усі налаштування зчитуються під час старту рантайму з файлу конфігурації `.env` або системних змінних оточення.

### Обов'язкові змінні оточення:
* `GATEWAY_PORT` — Порт для прийому вхідних підключень клієнтів (наприклад, `8443`).
* `CONTROL_PORT` — Порт виділеного каналу керування (Control Plane) для бекендів (наприклад, `8500`).
* `BACKEND_CONFIG_PATH` — Шлях до JSON/YAML файлу з архітектурним описом портів бекенд-серверів.
* `LOG_LEVEL` — Рівень деталізації логів для фреймворку `tracing` (`error`, `warn`, `info`, `debug`, `trace`).

## 3. Технічні вимоги до обробки транспортів (Вхідний шар)
Шлюз повинен одночасно відкривати та обслуговувати системні сокети у роздільних просторах TCP та UDP на значенні порту `GATEWAY_PORT`. Кожен транспорт зобов'язаний реалізувати власний ізольований шар **фреймінгу (Framing)** для виділення меж одного атомарного JSON-RPC повідомлення.

### 3.1. Базові транспорти (15 протоколів)
1. **`tcp`** — Потоковий транспорт. Фреймінг реалізується через роздільник символу нового рядка (`\n`). Кожне повідомлення має бути компактним (без зайвих переносів рядків усередині JSON).
2. **`tls`** — Аналогічний newline-фреймінг (`\n`), що працює поверх захищеного TLS-з'єднання.
3. **`udp`** — Сирі датаграми. Одне повідомлення дорівнює одному UDP-пакету. На рівні шлюзу має бути реалізована прикладна надійність: механізм підтверджень (ACK), тайм-аути для повторних спроб (Retries) та ковзне вікно дедуплікації пакетів.
4. **`rtp`** — Інcapsulation JSON-RPC всередину корисного навантаження (payload) RTP-пакетів. Контроль з'єднання, keepalive-метрики та прикладна надійність (ACK) реалізуються через RTCP APP (Application-defined) трафік.
5. **`rudp`** — Власний надійний датаграмний профіль поверх UDP. Шлюз самостійно контролює порядкові номери пакетів (Sequence Numbers), обробляє вікна ACK та виконує повторне надсилання втрачених датаграм.
6. **`srt`** (Secure Reliable Transport) — Нативна інтеграція через `libsrt` (або сумісний Rust-crate). Забезпечує надійну доставку повідомлень із вбудованим контролем перевантаження мережі та шифруванням за паролем (Passphrase).
7. **`udplite`** — UDP-Lite (RFC 3828) з налаштовуваним частковим покриттям контрольної суми (Checksum Coverage). Додаток реалізує прикладну надійність для специфічних платформ (Linux/Android).
8. **`dccp`** (Datagram Congestion Control Protocol) — Робота через під'єднаний датаграмний носій із вбудованими алгоритмами керування перевантаженням (Congestion Control), але без гарантії доставки пакетів операційною системою (Linux/Android).
9. **`sctp`** — Під'єднана SCTP-асоціація. Використовує нативну властивість SCTP зберігати межі повідомлень (Message Boundaries) без необхідності додаткового прикладного фреймінгу.
10. **`mqtt`** — Клієнтський шлюз підключається до зовнішнього MQTT 3.1.1 брокера. Запити клієнтів зчитуються з однієї черги (Inbox топік), а відповіді публікуються в Outbox топіки.
11. **`coap`** (Constrained Application Protocol) — Обмежений піднабір CoAP поверх UDP. Шлюз виступає як CoAP-сервер, парсить CoAP-запити та витягує JSON-RPC із корисного навантаження пакета.
12. **`amqp`** — Робота через зовнішній AMQP 0-9-1 брокер (наприклад, RabbitMQ). Повідомлення маршрутизуються через черги запитів/відповідей із обов'язковим відстеженням заголовка `correlation_id`.
13. **`http1`** — Прийом HTTP/1.1 `POST /` запитів. Тіло (Body) кожного запиту містить сирий JSON-RPC. Шлюз термінує HTTP-сесію та забирає payload.
14. **`quic`** — Нативний QUIC-протокол. Один повний обмін (Запит-Відповідь) відбувається в межах одного виділеного двонапрямного QUIC-стріму (Stream-level isolation).
15. **`http3`** — Обробка HTTP/3 `POST /` запитів. Кожен окремий запит автоматично ізолюється операційною системою в індивідуальний request stream.

### 3.2. WebSocket-style адаптери (14 протоколів)
Усі адаптери цієї групи (`ws-tcp`, `ws-udp`, `ws-rtp`, `ws-rudp`, `ws-srt`, `ws-udplite`, `ws-dccp`, `ws-sctp`, `ws-mqtt`, `ws-coap`, `ws-amqp`, `ws-http1`, `ws-quic`, `ws-http3`) зберігають базову семантику WebSocket-повідомлень (розподіл на Text/Binary фрейми, обробка Control-фреймів Close/Ping/Pong).
* Шлюз виступає в ролі **WS-термінатора**. Він знімає WebSocket-style envelope (конверт) з відповідного фізичного носія (наприклад, з SCTP-асоціації для `ws-sctp` або з CoAP-повідомлення для `ws-coap`) і виділяє чистий бізнес-текст або бінарний масив.

### 3.3. Особливість обробки WebSocket over TLS (`wss://`)
* Схема `wss://` не виділяється в окремий транспортний тип, а є **захищеним TLS-режимом нативного `ws-http1` адаптера**.
* Оскільки внутрішній WebSocket/HTTP/1.1 парсер шлюзу очікує на вхід звичайний (сирий) TCP потік даних, TLS-термінація має гарантовано відбуватися **перед** передачею байтів у WebSocket-адаптер. Це реалізується або через зовнішній upstream проксі (наприклад, Nginx/HAProxy), або за допомогою вбудованого в демультиплексор TLS-шару (`tokio-rustls`), який після розшифрування перенаправляє чистий потік у HTTP-парсер додатка.

## 4. Внутрішня уніфікація даних (Message Bus)
Для ізоляції ядра балансування від 29 способів доставки, будь-який вхідний транспортний шлюз після успішного виділення меж повідомлення зобов'язаний запакувати дані в єдину структуру-конверт `IncomingEnvelope` та надіслати її в асинхронний канал `tokio::sync::mpsc::unbounded_channel`.

### Специфікація абстракцій на Rust:
```rust
pub enum MessageFrame {
    Raw(bytes::Bytes),           // Для базових 15 протоколів
    WebSocketText(String),       // Для WS-адаптерів (текст)
    WebSocketBinary(Vec<u8>),    // Для WS-адаптерів (бінарні дані)
}

pub struct IncomingEnvelope {
    pub payload: MessageFrame,
    pub source_transport: TransportType,
    pub connection_id: String,   // Унікальний UUID сесії клієнта, згенерований шлюзом
    pub responder: tokio::sync::oneshot::Sender<MessageFrame>, // Канал для повернення відповіді у транспорт
}
```

## 5. Логіка балансування та Взаємодія з бекендами
1. **Алгоритм розподілу:** Шлюз виконує розподіл повідомлень за класичним принципом **Round Robin** із використанням потокобезпечних атомарних лічильників (`std::sync::atomic::AtomicUsize`).
2. **Адаптивна трансляція протоколів (Protocol Translation):**
   Балансувальник аналізує карту підтримуваних портів обраного бекенда (з конфігураційного файлу).
    * *Нативний роутинг:* Якщо бекенд підтримує той самий транспорт, з якого прийшов клієнт, шлюз передає повідомлення "як є".
    * *Конвертація типів:* Якщо транспорти відрізняються, шлюз на льоту перепаковує дані. (Наприклад: запит прийшов від клієнта по `ws-http1` у форматі `MessageFrame::WebSocketText`. Балансувальник обрав бекенд, який для цього типу повідомлень слухає тільки чистий `tcp`. Шлюз витягує рядок із фрейму, додає в кінець `\n` і відправляє в TCP-порт бекенда. Отриману відповідь шлюз конвертує назад у WebSocket Text Frame).
3. **Connection Pooling (Серверний пул):** Балансувальник зобов'язаний підтримувати асинхронний пул постійно відкритих ("гарячих") з'єднань (`Mutex<HashMap<TransportType, Vec<BackendConnection>>>`) до кожного порту бекенда. Створення нового мережевого handshake на кожен окремий RPC-запит суворо заборонено для мінімізації латентності. Пул повинен містити логіку періодичної валідації (очищення мертвих чи закритих за таймаутом сокетів).

## 6. Двосторонній зв'язок (Server-Initiated Push)

### 6.1. Реєстр сесій (Session Registry)
Шлюз утримує в оперативній пам'яті глобальну потокобезпечну колекцію активних користувачів (`DashMap<String, Arc<ClientSession>>`). Кожна сесія містить `mpsc::unbounded_channel` канал запису, підключений до асинхронної таски клієнтського транспорту.

### 6.2. Керуючий канал Control Plane (Порт `CONTROL_PORT`)
Шлюз відкриває виділений порт (за замовчуванням `8500`) виключно для прийому службових команд від внутрішніх бекенд-серверів. Команди передаються у форматі JSON, розділеному символом `\n`.

#### Підтримувані типи команд (Специфікація JSON):
* **Реєстрація бізнес-ID клієнта (після успішної авторизації на бекенді):**
  `{"action": "register_client", "connection_id": "UUID_ЗГЕНЕРОВАНИЙ_ШЛЮЗОМ", "client_id": "user_id_999", "groups": ["premium", "eu_region"]}`
* **Адресний пуш (Unicast):**
  `{"action": "push_unicast", "client_id": "user_id_999", "payload": "{\"jsonrpc\":\"2.0\",\"method\":\"notifyBalance\",...}"}`
* **Груповий пуш (Multicast):**
  `{"action": "push_multicast", "group_id": "premium", "payload": "..."}`
* **Загальна розсилка (Broadcast):**
  `{"action": "push_broadcast", "payload": "..."}`

### 6.3. Обмеження та Адаптація Пушу
Доставка ініційованих сервером пуш-повідомлень гарантується **виключно для клієнтів, які використовують двонаправлені транспорти** (`tcp`, `tls`, `quic`, `mqtt`, `amqp`, `sctp`, `srt` та їхні `ws-` аналоги).
Будьте обачні, використовуючи код.
• Поведінка для двонаправлених транспортів: Шлюз знаходить сесію клієнта, визначає поточний транспорт і автоматично адаптує пуш (додає \n для tcp, загортає у WS Text Frame для ws-tcp, ініціює новий Server-Initiated Stream для quic або публікує в персональну чергу пушів на MQTT/AMQP брокері).
• Поведінка для однонаправлених транспортів: Якщо бекенд намагається надіслати пуш для клієнта, який підключений через транзитний транспорт (наприклад, http1 POST або сирий udp без прикладного сесійного шару), шлюз миттєво відхиляє команду та повертає бекенду в Control Plane сокет помилку:
{"success": false, "error": "PushNotSupportedForTransport"}. Шлюз не повинен накопичувати черги повідомлень у пам'яті для таких клієнтів.

7. Нефункціональні вимоги та Продуктивність

• Мова та Стандарти: Безпечний Rust (Stable), редакція edition = "2021".
• Рантайм: Асинхронний багатопотоковий tokio (Work-stealing scheduler) для максимального масштабування обробки сокетів на всі доступні ядра процесора.
• Ефективність роботи з пам'яттю (Zero-Copy): Використання атомарно-керованих буферів bytes::Bytes для виключення дублювання та копіювання масивів байтів під час трансляції між клієнтським шлюзом та серверним пулом з'єднань.
• Заборона на парсинг: Повний десеріалізаційний аналіз основного бізнес-трафіку JSON-RPC на шлюзі суворо заборонено (за винятком вилучення технічних метаданих у HTTP-заголовках, CoAP або заголовках WS-фреймів). Робота з serde_json дозволяється виключно для службових команд на Control Plane порті.
• Діагностика: Наскрізне асинхронне логування через макроси фреймворку tracing. Кожен етап (вхідний конект, виділення фрейму, вибір бекенда з пулу, реєстрація пуш-команди) має фіксуватися у структурованому вигляді без блокування основного потоку виконання.

8. Критерії приймання системи (Acceptance Criteria)

1. Шлюз стабільно запускається, зчитує змінні з .env та успішно ініціалізує мережеві слухачі на зазначених портах.
2. Запити від клієнтів з будь-якого підтримуваного транспорту успішно проходять шар фреймінгу, проксіюються через ConnectionPool на бекенд у потрібному форматі, а відповіді повертаються клієнту без спотворень.
3. Зміна мережевого інтерфейсу клієнтом на QUIC-транспорті (імітація Connection Migration) коректно обробляється шлюзом на основі збереження Connection ID (пакети продовжують летіти на той самий бекенд).
4. Команди адресних, групових та загальних розсилок від бекендів через порт Control Plane миттєво доставляються активним клієнтам з автоматичною адаптацією під структуру їхнього поточного транспорту.
5. Спроба надіслати пуш на однонаправлений транспорт (http1) коректно відхиляється з поверненням відповідного коду помилки.
6. Примусове закриття сокета клієнтом (або Close Frame у WS-адаптерах) призводить до негайного повного очищення його даних із глобального SessionRegistry для запобігання витоків оперативної пам'яті.
